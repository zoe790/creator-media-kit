# Publishing the repository

The repository root is the skill package: SKILL.md, README.md, agents, scripts, references, assets, and LICENSE. Prepare a local release when no destination has been specified; do not guess a GitHub owner or treat an example repository as the publication target.

Use English for public documentation, discovery metadata, fixed template copy, and demonstration assets. Keep the project's first-person story grounded in the author's stated experience: creator enquiries arriving through WeChat, email introductions, and a desire for a portfolio that opens directly in a conversation. Do not invent customers, fundraising progress, measured conversion improvements, or adoption figures.

Only include fictional demo briefs, generic templates, scripts, and licensed fonts. Real user tests, recordings, extracted frames, account links, and contact details belong outside the public package. Publish a real customer example only when explicitly authorized for that purpose.

Before release, run the behavioral tests and render the fictional demo. Review the actual images and verify that the README preview matches the current English templates. Inspect the file list for credentials, environment files, browser state, private briefs, machine-specific paths, and unapproved images. A gitignore does not remove previously tracked files.

Retain the MIT license and third-party notices. Document the host capabilities and dependencies honestly: build.py reads local data; it is not a URL crawler or a standalone recording parser. Do not promise permanent platform access or exact data from inaccessible pages.

Once the user supplies the destination and authorizes publication, use an available GitHub connector or CLI and verify the remote result. Until then, describe the package as locally prepared, not published.
